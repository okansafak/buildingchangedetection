# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

GeoChange AI ("Atlas GeoChange" in the UI) is a Flask prototype that detects building changes (new / demolished / existing) between two satellite images (T1, T2), vectorizes them to GeoJSON, and shows them in a single-page web UI. All user-facing strings, API error messages, and CSV headers are in **Turkish**; keep new UI text and messages in Turkish too.

## Commands

No build step or linter config. `pip install -r requirements.txt` (Python 3.10+): `flask`, `flask-cors`, `opencv-python-headless`, `numpy`, `pillow`, `onnxruntime`, `huggingface_hub`, `pyproj`, `tifffile`, `pytest`. `torch`/`torchvision` are not used (the README's PyTorch description is aspirational). The first ML detection downloads the ONNX model into `models/` (gitignored): the ~396 MB fp32 model on an NVIDIA GPU, else the ~141 MB int8 model. GPU: `requirements-gpu.txt` (`onnxruntime-gpu[cuda,cudnn]`, replaces `onnxruntime`; never install both); `run.bat` switches to it automatically when `nvidia-smi` exists. `ATLAS_DEVICE=cpu` forces the CPU.

```bash
python app.py                 # serves http://127.0.0.1:5000, or $PORT (debug=False, binds 0.0.0.0)
python -m pytest                   # offline test suite; pytest.ini limits collection to tests/
python -m pytest tests/test_projects_api.py::test_project_roundtrip -v   # single test
python parse_wayback.py       # rebuild wayback_releases.json from Esri's WMTS capabilities
```

`run.bat` is a Windows launcher (activates `.venv`/`venv` if present, installs `requirements.txt` when a dependency is missing, picks the first free port from 5000 unless `PORT` is set, runs `app.py` from the repo root). On Windows a busy port (e.g. a Docker container on 5000) does not make Flask fail to bind: requests get split between both servers, showing up as 401/404s and CSS served as JSON. Root-level `test_wayback.py` is an ad-hoc network script, not a pytest test. `tests/snapshots/` pins the exact API output. If a snapshot test fails after a change, the change altered behavior: fix the code, and regenerate with `python -m pytest --update-snapshots` only for an intentional behavior change. Snapshots pin the classic engine only (the LEVIR-CD / DSIFN pairs in `tests/fixtures/samples/` are test data, not app samples); tests never load the real ML model — `tests/fakes.py` (`FakeSegmenter`, `FakeSession`, `OfflineSegmenter`) stands in for it, and the `app_module` fixture runs jobs synchronously. An OpenCV/NumPy upgrade or a different CPU can also shift overlay hashes or last-digit floats (PNG encoder builds and NumPy's SIMD `np.cos` differ), so confirm that (e.g. re-run on the previous commit) before changing code. Run everything from the repo root: `LiveSatelliteFetcher` (`static/live_cache`) and `ProjectManager` (`data/`) use cwd-relative paths, while `app.py` resolves samples/uploads via `app.root_path`.

## Architecture

**Backend** — [app.py](app.py) holds all routes and module-level singletons (`detector`, `ml_detector`, `jobs`, `live_fetcher`, `project_mgr`). Detection requests take `engine`: the API default is `"classic"` (`BuildingChangeDetector`, pinned by snapshot tests), and the UI always sends `"ml"` (`MLChangeDetector`). Input paths:
- `/api/detect` with `scenario_id: "custom"` (the only accepted value; the app ships no sample datasets) and server file paths returned by `/api/upload` (they must resolve inside `UPLOAD_FOLDER`). With `engine: "ml"` it validates synchronously, then answers **202** `{job_id}`; the client polls `GET /api/jobs/<id>` (`status`, `progress`, Turkish `stage`, `result`). ML options: `analysis_mode` `"fast"`/`"deep"`, `manual_georef` `{bounds?, gsd?, epsg?}`.
- `/api/upload` — `image_t1/t2` plus optional `world_t1/t2` and `prj_t1/t2` sidecars (saved next to the image with the same stem); returns `georef_A/B` summaries or `georef_A/B_error`, and JPEG preview URLs for TIFFs. 413 is JSON (limit `MAX_UPLOAD_MB`).
- `/api/live/preview` and `/api/live/detect` — `LiveSatelliteFetcher` downloads and stitches a `grid_size`×`grid_size` grid (1–8, default 2) of 256 px zoom-17 Esri Wayback tiles for each year, centred on the point, returning images plus WGS84 `bounds` and GSD. The request's `zoom` is ignored (it is the map view zoom; analysis is always zoom 17). The UI calls `preview` for step 2 (imagery only) and `detect` with `engine: "ml", job: true` from the step-2 button (202 + job, like `/api/detect`); without `job` it runs synchronously. Model load failure → 503 (sync) or a job error. The map picker draws the exact tile grid (`drawLiveArea`, same maths as `geo.centred_grid_origin`) for the side length typed in metres.

The latest result is stored in the global `LAST_RESULTS['latest']`; `/api/export/geojson` and `/api/export/csv` read from it (single-user, in-memory). Opening or saving a project also overwrites `LAST_RESULTS` so exports match the loaded project.

**Detector** — [model/change_detector.py](model/change_detector.py) is classical OpenCV, *not* a neural net (the README's "PyTorch SiamUnet" description is aspirational). Pipeline: weighted grayscale + LAB difference map → threshold + morphology → contours → classify each as new/demolished using T1 vs T2 edge density and brightness → Canny-based candidates in T2 that don't overlap changes become "existing" (capped at 25). `detect()` orchestrates private step methods; every building's record and GeoJSON feature is produced by `_build_record`, and per-type labels, colors and mask values live in `BUILDING_TYPES`. Pixel coordinates are mapped linearly into `bounds = [south, west, north, east]`. When a ground-truth label is supplied (benchmarks with `use_gt`), the classic engine blends it into the diff map at 80% weight, so its benchmark output is largely GT-driven; the ML engine instead reports precision/recall/F1/IoU in `metrics`.

The `detect()` return dict is the contract with the frontend and is persisted verbatim as a project's `results_data`: `stats`, `buildings` (each with geo `centroid` and pixel `px_coords`), `geojson`, and `overlays` (base64 PNG data URIs for mask, heatmap, T1, T2).

**ML engine** — [model/ml_detector.py](model/ml_detector.py) returns a superset of that contract (`engine`, `analysis_mode`, `georef`, `metrics`, `stats.total_changed_px`, per-building `area_px`). [model/segmenter.py](model/segmenter.py) runs the pinned ChangeStar ViT-B ONNX model (HF `geobase/changestar-building-segmentation-vitb`) over overlapping **1024 px** tiles (the export has fixed positional embeddings) for each date: CUDA fp32 when available (`arena_extend_strategy=kSameAsRequested` + `enable_mem_pattern=False`, ~0.6 s/tile on a 4 GB RTX 3050; the defaults spill out of VRAM and are no faster than the CPU), otherwise — or after any CUDA error mid-image, which redoes the image — the CPU int8 model (~10 s/tile); results report `device`; [model/object_change.py](model/object_change.py) matches the two building masks as connected components with a parallax tolerance (`PARALLAX_TOLERANCE_M = 8`: off-nadir roofs move between dates) into new / demolished / existing, splitting partially supported objects. `analysis_scale`: "fast" halves images larger than 2048 px (unless the halved GSD would exceed 1.2 m) and never enlarges them; otherwise imagery of 0.75 m/px or coarser (Wayback) is upsampled up to 2× toward 0.5 m, and "deep" keeps native resolution. Without a georeference, results stay in pixels: `bounds`, `georef` and every `centroid` are `null`, GeoJSON has `"georeferenced": false` with pixel coordinates, and areas are m² only when a GSD is known. Job results write overlays to `static/results/<run_id>/` (gitignored) and reference them by URL (T1/T2 are JPEG despite the `*_png_base64` keys), so projects saved from ML runs depend on that folder. [model/jobs.py](model/jobs.py) is a single-user in-memory thread runner. [model/georef.py](model/georef.py) reads GeoTIFF tags, world files (+ `.prj`) and manual WGS84 bounds into a `GeoRef` (GDAL-style affine + CRS, converted with pyproj); T1 is always resized onto T2's grid, and two georeferenced images covering different areas are rejected.

**Wayback releases** — [model/live_satellite.py](model/live_satellite.py) maps years to Esri Wayback release IDs in `WAYBACK_RELEASES` (curated by hand from `wayback_releases.json`), and defines `LIVE_HOTSPOTS`. The grid is centred on the requested point (`geo.centred_grid_origin`). `tests/test_hotspot_catalog.py` keeps the Discover cards and the hotspot select in `templates/index.html` in sync with `LIVE_HOTSPOTS` (ids and years); hotspots were chosen where the ML engine gives clear results (residential growth), since giant industrial roofs and off-nadir towers are its weak spots. Missing historical tiles become gray placeholder tiles on purpose (falling back to current imagery would make T1 == T2); `placeholder_tile_mask` finds them, `_live_detect` passes them to the detector as `invalid_mask` (no buildings there) and adds a Turkish `warnings` entry, preview reports `missing_tiles`, and if a date has no imagery at all the request fails (422 / job error). A release year is only the basemap snapshot: `capture_info` queries Esri's per-release metadata service (`waybackconfig.json` → `metadataLayerUrl`, layer 6 for zoom 17) for the real acquisition date/source/resolution (e.g. the "2014" release shows 2011 imagery in Austin); preview and detect return it as `capture`, the UI shows "2014 · çekim 2011-02" and warns when both years show the same capture. Lookups are cached per release and rounded location; failures (the service has 503 outages) return `null` and are not cached. Tiles are cached as `static/live_cache/{release}_{zoom}_{y}_{x}.jpg`.

**Geo math** — [model/geo.py](model/geo.py) holds all bounds, pixel↔lon/lat and Web Mercator tile math as pure functions; bounds are always `[south, west, north, east]`. Snapshot tests compare floats exactly, so keep operation order (and numpy vs `math`) when editing it.

**Persistence** — [model/project_manager.py](model/project_manager.py) uses SQLite at `data/projects.db`; `coords`, `stats`, `results_data` are JSON-encoded TEXT columns. `list_projects` omits `results_data`, and search filtering happens in Python. `data/projects.json` is a legacy file that nothing reads.

**Frontend** — [templates/index.html](templates/index.html) + [static/js/app.js](static/js/app.js) (vanilla JS, one global `state` object, DOM refs in `el`) + [static/css/style.css](static/css/style.css). There are two screens, `dashboard` (project list) and `workspace`, and a 3-step wizard (1: pick source, 2: preview, 3: results). Leaflet with Esri imagery is used only for picking a location in step 1. Results are rendered in pixel space on a custom image-swipe stage (T2 underneath, clipped T1 on top, with pan/zoom and SVG polygons from `px_coords`), not as geo-overlays on a map. Detection settings and custom collections are stored in `localStorage` (`atlas_*` keys) and sent with each request. `runDetectionJob` posts ML detections and polls `/api/jobs`, showing progress on the run button; with thousands of buildings the sidebar lists every changed one but at most `MAX_EXISTING_CARDS` existing ones.
